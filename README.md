# Cardiovascular Disease Prediction

## 1. Project Overview
This project develops a machine learning architecture capable of predicting the likelihood of cardiovascular disease based on clinical patient features. 

The repository has recently transitioned from a set of experimental prototype scripts into a mature, production-oriented **MLOps architecture**. This structured pipeline rigorously separates model development, evaluation, and production serving to prevent data leakage and guarantee reproducibility.

> **IMPORTANT CLINICAL DISCLAIMER:**
> This is a machine-learning research and engineering project designed for exploring algorithmic classification and MLOps principles. **It is not a clinically validated diagnostic system** and must not be used for actual medical diagnosis.

## 2. Architecture
The complete end-to-end lifecycle follows a strict MLOps flow:

```text
Raw Dataset
     ↓
Dataset Validation & Integrity Checks
     ↓
Train/Holdout Split (Isolated)
     ↓
Development Pipeline (Stratified K-Fold CV)
     ↓
Model Comparison & Candidate Selection
     ↓
Champion / Challenger Evaluation
     ↓
Final Holdout Evaluation
     ↓
Model Registry
     ↓
Production Pipeline
     ↓
Prediction & Probability Serving
```

## 3. Model Development
The development pipeline systematically evaluates the following algorithm candidates:
1. Logistic Regression
2. KNN
3. Random Forest
4. Extra Trees
5. Gradient Boosting
6. XGBoost
7. CardioStack v2

Models are evaluated using Stratified K-Fold cross-validation. The project prioritizes the minimization of false negatives and ranks candidates systematically:
**Primary:** Recall → **Tie-Breaker 1:** F1 Score → **Tie-Breaker 2:** ROC-AUC.

The isolated holdout test set is strictly prohibited from being accessed during this iterative development phase.

## 4. CardioStack v2
The authoritative ensemble architecture of this project is **CardioStack v2**. It implements a parallel stacking strategy using Scikit-Learn's `StackingClassifier`:
*   **Parallel Base Learners:** Random Forest, XGBoost, ExtraTrees
*   **Meta-Learner:** Logistic Regression

The meta-learner is inherently trained using out-of-fold cross-validated predictions generated by the base learners. The base estimators do *not* feed into one another sequentially.

## 5. Leakage Prevention
Data leakage is rigorously prevented across the pipeline:
*   **Training/Holdout Separation:** The holdout set (`test.csv`) is written once and completely sealed from the development pipeline.
*   **Preprocessing Isolation:** A Scikit-Learn `ColumnTransformer` explicitly separates target variables and fits preprocessing parameters (medians, scalers, vocabularies) **only** on the active training fold.
*   **Validation Transformation:** Holdout and validation data are transformed blindly without refitting.

## 6. Development Pipeline
Command:
```bash
py run_development.py
```
**Function:** Loads only the training data and evaluates all candidate models using a unified preprocessing pipeline across Stratified K-Fold cross-validation. It outputs a comprehensive comparison report (`results/development_results.json` and `model_comparison.csv`) ranking the models. It **does not** deploy or promote a production model.

## 7. Promotion Pipeline
Command:
```bash
py run_promotion.py
```
**Function:** Identifies the algorithmic winner from the development pipeline to act as a **Challenger**. The Challenger is then trained on the complete training set and evaluated exactly once against the untouched holdout test set. If the Challenger passes predefined quality gates, it is compared against the currently active **Champion**. 
Passing quality gates does *not* automatically trigger promotion; it must objectively outperform the active champion. If successful, the artifact is serialized and registered.

## 8. Production Pipeline
Command:
```bash
py run_production.py
```
**Function:** Provides simulated live inference. It securely queries the registry for the `active_version`, loads the specific native `model_vN.pkl` artifact into memory, validates the incoming raw patient payload against a strict schema, and returns a JSON response containing the binary prediction, calculated probability, and model metadata. 
**Production is purely an inference consumer and never retrains or refits models.**

## 9. Model Registry
The registry system governs model deployment and traceability.
*   **`registry/registry.json`:** The single source of truth tracking historical evaluations, versioning (`v1`, `v2`, etc.), promotion status, and the `active_version`.
*   **`registry/artifacts/`:** Local storage for versioned model artifacts referenced by the registry.
*   **Rollback:** Previously promoted model versions can be restored by changing the registry's active_version; the production inference layer detects the version change and reloads the corresponding artifact.

## 10. End-to-End Usage
A normal full lifecycle execution follows this sequence:
```bash
# 1. Evaluate algorithms and rank candidates on training folds
py run_development.py

# 2. Evaluate the top candidate on the holdout test set and promote if superior
py run_promotion.py

# 3. Serve the active champion to process new raw patient features
py run_production.py
```

## 11. Validation Scripts
The project includes a suite of integration validations that test the architectural guarantees:
*   `py validate_phase1.py`: Verifies canonical dataset integrity, eliminates duplicates, and proves reproducible deterministic splitting.
*   `py validate_phase2.py`: Verifies the `ColumnTransformer` handles unseen categories securely and does not suffer from global fitting leakage.
*   `py validate_phase3.py`: Validates the CardioStack v2 StackingClassifier architecture and its isolation capabilities.
*   `py validate_phase4.py`: Verifies that the Stratified CV development pipeline correctly ranks models without touching the test set.
*   `py validate_phase5.py`: Validates the Champion/Challenger promotion lifecycle and quality gate enforcement on holdout data.
*   `py validate_phase6.py`: Verifies production inference safely rejects illegal schemas (like target variables) and executes clean predictions.
*   `py validate_phase7.py`: Verifies the registry successfully validates corrupted artifacts, maintains historical metadata, executes rollbacks, and triggers dynamic cache reloads in production.

## 15. Future Work / Technical Debt
The core MLOps architecture (Phases 1–8) is complete. Future maintenance and scalability improvements include:
*   **API Service Integration:** Wrapping `run_production.py` inside a FastAPI or Flask service for network-accessible HTTP JSON inference.
*   **Data Drift Detection:** Implementing statistical divergence checks to flag when live production payloads meaningfully drift from `train.csv` distributions.
*   **Dependency/Version Locking:** Migrating from a basic `requirements.txt` to a hardened lockfile solution (e.g., pip-tools, Poetry) for exactly reproducible builds.
*   **Legacy Code Deletion:** Permanently removing the `archive/legacy/` experimental code and old tainted `models/*.pkl` artifacts to reduce repository footprint.

## 16. Core Design Principles
1.  **Holdout Isolation:** Never use holdout data for iterative development.
2.  **Objective Promotion:** Do not promote a model merely because it passes minimum quality gates; it must demonstrably beat the active champion.
3.  **Artifact Immutability:** Never overwrite production artifacts without a formal registry promotion.
4.  **Single Source of Truth:** Production always queries the registry's `active_version`.
5.  **Leakage-Free Constraints:** Preprocessing logic must remain isolated per-fold.
6.  **Code Segregation:** Legacy/experimental code must remain physically isolated in `archive/legacy/`.
